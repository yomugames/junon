# Outcome

Players who run Junon through Steam can host co-op and invite Steam friends
without port forwarding, a VPN or typing an address. A friend joins from a
Steam invite, from "Join Game" in the Steam friends list, or from the Join
panel's list of friends who are hosting. Traffic goes over Steam Networking
Sockets (peer-to-peer through the Steam Datagram Relay), so neither side's IP
address is exposed and NAT doesn't matter.

Acceptance criteria:

- With Steam running and the game launched through Steam, the host clicks
  "Host on Steam" and the world is open to Steam friends. The host can open
  the Steam invite dialog from the Host panel.
- A friend accepts the invite (game running or not) or uses "Join Game", and
  lands in the host's world as their own character. Leaving and rejoining keeps
  that character, including from a different machine with the same Steam
  account.
- Direct-address (LAN / port forwarding) co-op keeps working unchanged, and
  both can be open at once.
- Without Steam (not installed, not running, `npm run server`, browser client),
  the game behaves exactly as today and the Steam controls are hidden.
- A guest can't impersonate another Steam user or the host: the host derives
  a Steam guest's identity from the authenticated connection, not from
  anything the guest sends.
- Hosting ends as it does now (stop, switch world, quit): Steam guests get
  `PlayerKick` with a reason and the Steam lobby is left.

## Context

- Co-op today is a listen server: [ARCHITECTURE.md](../../../ARCHITECTURE.md)
  and Phase 6 of
  [electron-offline-coop.md](electron-offline-coop.md). Guests connect a
  WebSocket to a second listener (`StandaloneSocketServer#openGuestListener`);
  those sockets are marked `isGuest`, and `Server#authorizeGuest` checks the
  protocol hash and the password proof before upgrade.
- The game server never touches `ws` directly. It talks to
  `StandaloneSocket` (`server/util/standalone_socket_server.js`), which
  exposes `send(data, isBinary)`, `close()`, `end()`, `remoteAddress` and
  `isGuest`. A Steam connection can be another implementation of that shape,
  so `SocketUtil`, `Game` and `Player` need no transport changes.
- The client opens its socket in one place, `GameConnection#setupSocket`
  (`client/src/components/game_connection.js`), using `onopen`, `onmessage`,
  `onerror`, `onclose`, `send`, `close` and `binaryType = "arraybuffer"`.
- Process layout (`packages/junon-desktop`): Electron main serves the client
  and relays preload IPC; the game server runs in a utility process and talks
  to main over its parent port (`Server#initDesktopChannel`). The renderer is
  sandboxed, context-isolated, with one preload API (`window.junonDesktop`).
- Identity: players are local profile ids generated by the client
  (`client/src/util/local_profile.js`); characters are keyed by that uid.
  Guests' uids are self-asserted, which is acceptable on a password-protected
  LAN host but not as the only identity for a Steam guest.
- Per-IP checks in `Game#performJoinGame` (`game.js` ~1998, 2015, 2084, 2103)
  use `socket.remoteAddress`: a 2-player-per-IP limit and team IP bans.
- Messages: `SocketUtil` sends text (JSON) and binary (protobuf) frames; the
  socket payload limit is 16 MB. Steam Networking Sockets caps one message at
  512 KB (`k_cbMaxSteamNetworkingSocketsMessageSizeSend`), so large frames
  (the initial sector) must be fragmented.

## Implementation

### Milestone 1: Steam runtime

1. Add `steamworks-ffi-node` to `packages/junon-desktop` only. It is loaded
   lazily by a new `src/steam.js`; any failure (library missing, Steam not
   running, init false) leaves `steam.isAvailable === false` and logs one
   line. Nothing else in the app may require the binding directly.
2. App id from `JUNON_STEAM_APP_ID`, falling back to the real app id once
   assigned (480 "Spacewar" for development only; never shipped). In
   packaged builds call `restartAppIfNecessary` so a game launched outside
   Steam relaunches through it.
3. Run `runCallbacks()` on a short main-process interval (~16 ms while a
   Steam connection is open, ~100 ms otherwise) — required for networking,
   lobby and join callbacks.
4. Attach the Electron overlay (`addElectronSteamOverlay(mainWindow)`) behind
   a flag until it is checked on all three platforms; invites work without
   it (the invite dialog opens in the Steam client).
5. Extend the preload API with `junonDesktop.steam`: `getStatus()`
   (available, persona name, Steam id), `onJoinRequest(handler)`, and the
   host/guest calls from Milestone 3. Main checks `isAppFrame` as for
   `localWorldApi` and allowlists methods.

The Steam SDK must be initialized once, in the main process. The game server
stays Steam-free: it only sees sockets.

Done as follows. `src/steam.js` (`SteamRuntime`) requires the binding inside
`init()`, so a missing package or redistributable can't stop the app.
`JUNON_STEAM=0` turns it off; `JUNON_STEAM_APP_ID` defaults to 480;
`JUNON_STEAMWORKS_SDK` points at an SDK outside the repository. After init it
calls `initRelayNetworkAccess()` and polls `runCallbacks()` plus
`networkingSockets.runCallbacks()` every 10 ms while a Steam connection is
open, else every 100 ms, followed by the host and guest relays' `poll()`.
`shutdown()` runs after the server has saved on quit. Preload has
`steam.getStatus()` and `steam.openSocket()`; `onJoinRequest` comes with
Milestone 3. Not done: the overlay (step 4, deferred until a machine with
Steam can check it; the binding's overlay renders the window into a native
surface, which may affect input) and `restartAppIfNecessary` (step 2, needs
the packaged build and the real app id).

### Milestone 2: transport

Wire format over a Steam connection (versioned, so it can change later):

```text
byte 0: frame kind   0 = text, 1 = binary
byte 1: fragment     0 = whole, 1 = first, 2 = middle, 3 = last
bytes 2..: payload   (at most 500 KB per Steam message)
```

All messages use `k_nSteamNetworkingSend_Reliable` on one connection, so
ordering is preserved and fragments reassemble in order. The receiver caps a
reassembled frame at the existing 16 MB `MAX_PAYLOAD_LENGTH` and closes the
connection beyond it. Framing lives in `junon-common/steam_framing.js` (pure,
no Steam dependency) so both main processes and Jest share it.

Host side:

1. On "Host on Steam", main creates a P2P listen socket
   (`createListenSocketP2P(JUNON_STEAM_VIRTUAL_PORT)`), accepts connection
   requests only from members of the host's current lobby, and assigns each
   connection a local id.
2. Main relays per-connection events to the utility process over the
   parent port: `steamOpen { id, steamId }`, `steamData { id, kind, bytes }`
   (after reassembly), `steamClose { id }`; and back: `steamSend`, `steamEnd`,
   `steamKill`.
3. On the server, `server/util/steam_socket_bridge.js` turns those into
   `SteamGuestSocket` objects with the `StandaloneSocket` shape:
   `isGuest = true`, `isSteam = true`, `steamId`, and
   `remoteAddress = "steam:" + steamId`. They are added to
   `standaloneSocketServer.sockets`, so idle closing, `stopHosting`'s kick
   loop and `onSocketClose` apply without change.
4. Protocol check: the guest's first message is a hello
   `{ protocol: <hash> }` frame handled by the bridge, not by game code. A
   wrong hash gets a close with a "Version mismatch" reason; the client shows
   it like the `/info` preflight does today. No password: Steam access is
   limited to the lobby (friends-only, or invite-only; see Decisions).

Guest side:

1. Main connects with `connectP2P(hostSteamId, virtualPort)` and relays
   open/message/close to the renderer through preload.
2. Preload exposes `junonDesktop.steam.openSocket(hostSteamId)` returning a
   minimal WebSocket-like object (`onopen`, `onmessage({ data })`,
   `onerror`, `onclose`, `send(stringOrArrayBuffer)`, `close()`,
   `readyState`). Data crosses the context bridge as strings and
   ArrayBuffers.
3. `GameConnection` gets an optional `options.openSocket(url)` factory; the
   default stays `new WebSocket(url)`. Steam joins pass the Steam factory
   with a `steam:<hostSteamId>` pseudo-URL. Reconnect (`attemptReconnect`)
   reuses the factory, so a dropped relay reconnects like a dropped socket.
   `getServerIp`/the `server_ip` cookie must not treat `steam:` URLs as
   addresses.

Done as follows, with these differences from the steps above:

- Control frames are a third frame kind (`KIND_CONTROL`, JSON), not a
  special text frame: guest `hello { version, protocol }`, host `welcome` or
  `reject { reason, code }` followed by a graceful close. The guest's main
  process sends the hello, and the renderer's socket only opens on
  `welcome`, so a refused guest sees a socket that failed to open, with the
  host's reason (`GameConnection` passes `event.reason` to `onPlayerCantJoin`).
- Main does the framing in both directions; the parent port carries whole
  frames (`steamOpen`, `steamFrame { kind, data }`, `steamClose`), plus
  `steamHosting { isHosting }` from the server, which opens and closes the
  P2P listen socket. A connection the server hasn't heard a hello on is
  refused after 15 s.
- Steam refuses reliable sends with `LimitExceeded` while its send buffer
  (512 KB by default, and the binding can't change it) is full.
  `SteamOutbox` holds the rest per connection and retries on every poll; a
  connection more than 64 MB behind is dropped.
- When the close and the last frames (the reject reason, a kick) arrive in
  the same callback run, the guest reads the frames first. The relay test
  found this.
- Server: `hostWorldOnSteam` (owner only, desktop only) sets
  `Server#steamHost`. `stopHosting` now ends LAN and Steam hosting together.
  `getHostingStatus` has `isOnSteam`, and `port` is null without a LAN
  listener. Steam guest sockets live in the socket server's set, so the idle
  timeout and the kick loop apply. `StandaloneSocketServer#endGuestSockets`
  ends them when only Steam was hosted.
- `server/util/desktop_channel.js` lets the server use Node IPC
  (`JUNON_DESKTOP_IPC=1`, `serialization: 'advanced'`) in place of Electron's
  parent port, so tests can play the main process.
- Main refuses `hostWorldOnSteam` when it has no Steam, since the server
  can't tell.
- Milestone 3 limited the listen socket to lobby members.

### Milestone 3: host and guest flows

1. Host panel: when `steam.getStatus().isAvailable`, show "Host on Steam"
   next to the address/port form, with lobby type (Friends only — default /
   Invite only). Starting it opens the world if needed (as `hostWorld`
   does), creates the lobby (`createLobby`, max members = game's player
   limit), sets lobby data `{ junon: 1, protocol, world: <name>, version }`,
   opens the listen socket, and tells the server (new local API method
   `hostSteam` / `stopSteamHosting`, or an extension of `hostWorld`; the
   server records `coopHost.steam = true` for `getHostingStatus` and
   `sendHostingStatus`).
2. "Invite friends" button → `overlay.activateGameOverlayInviteDialog(lobby)`.
3. Rich presence on the host: `status` ("Hosting <world>"), `connect`
   (`+connect_lobby <lobbyId>`) and `steam_player_group`, so "Join Game"
   works from the friends list. Cleared when hosting stops.
4. Guest entry points, all ending in the same `joinSteamLobby(lobbyId)`:
   - `GameLobbyJoinRequested` while running (invite accepted / Join Game);
   - launch command line (`getLaunchCommandLine` / `+connect_lobby` argv)
     when the game was started by the invite;
   - Join panel: a "Friends hosting on Steam" list from friends' rich
     presence / lobbies with `junon=1`.
   Join the lobby, read `protocol` from lobby data (mismatch → "Version
   mismatch" before connecting), then connect to the lobby owner's Steam id.
5. Ending: `stopHosting` (server) also notifies main to leave the lobby,
   close the listen socket and clear rich presence. Main does the same if the
   server process exits. A guest whose host left the lobby gets the existing
   disconnect handling.

Done as follows (main: `src/steam_lobby.js`, `main.js`; client:
`util/steam_coop.js`, `components/local_world_menu.js`):

- `hostWorldOnSteam` takes `lobbyType` (`friends` or `invite`, mapped to
  Steam's FriendsOnly and Private lobby types). The server's `steamHosting`
  message carries what main needs for the lobby: lobby type, world name,
  `maxMembers` (`Game#getMaxPlayers`, 20), protocol hash and game version.
  Main creates the lobby on that message, and its `hostWorldOnSteam` handler
  waits for it; if the lobby can't be created, it stops hosting again and
  reports the error. Lobby data: `junon=1`, `protocol`, `version`, `world`.
- Membership gate: a connection request waits up to 10 s for its Steam id to
  appear among the lobby's members (the host may see the request before the
  member list updates), then is closed. Without it, anyone who knew the
  host's Steam id could connect; the hello's protocol check isn't access
  control.
- Rich presence: `status` ("Hosting <world>", "Playing in <world>") and
  `steam_player_group`. No `connect` key: with it, Join Game would arrive as
  GameRichPresenceJoinRequested, which the binding doesn't expose. A host in
  a joinable lobby already gets Join Game, which arrives as
  GameLobbyJoinRequested. `status` only shows in the Steam client once
  localization tokens (`steam_display`) are set up for the real app id.
- Invites: Steam's overlay invite dialog, and a list of online friends with
  an Invite button each (`inviteUserToLobby`, a Steam chat invite), because
  the overlay isn't hooked into the Electron window yet (Milestone 1, step 4)
  and the dialog may not show without it.
- Join requests: GameLobbyJoinRequested goes to the renderer
  (`junon:steam-join-request`), and the lobby of a launch with
  `+connect_lobby <id>` (from argv, or `getLaunchCommandLine`) is reported
  once by `getStatus().pendingLobbyId`. Both join through the same path as
  the Join panel's list; with a world open, the player is asked first.
- Friends hosting: `getFriendGamePlayed` for each friend, keeping those in
  this app with a lobby, plus their `status`. Steam fills in the lobby for
  friends who are in one.
- Leaving: the guest leaves the lobby when the menu shows again (back from
  the world, kicked, or the host closed it). It stays in the lobby while
  disconnected, so the client's automatic reconnects still pass the host's
  membership gate. Main leaves both lobbies on quit. A player can't join a
  lobby while hosting one.
- Main-only Steam calls go through one `junon:steam-api` IPC with an
  allowlist (`getStatus`, `listFriends`, `listFriendsHosting`, `invite`,
  `openInviteDialog`, `joinLobby`, `leaveLobby`), replacing
  `junon:steam-status`.
- Tests: `test/support/fake_steam.js` is an in-memory Steam (sockets,
  lobbies, friends, rich presence, overlay) shared by `steam_relay.spec.js`
  and the desktop app, which loads it instead of the binding when
  `JUNON_STEAM_FAKE_SDK` is set. That seam is test-only, like
  `JUNON_DESKTOP_IPC`.

### Milestone 4: Steam identity

1. For Steam guest sockets, `Game#performJoinGame` ignores the
   client-supplied uid and uses `steam-<SteamID64>` as the character key; the
   client's profile name stays the display name. (Format matches the
   `imported-<n>` style; `getLocalProfileUid` must reject client-supplied
   `steam-` ids on non-Steam sockets so a LAN guest can't claim one.)
2. The owner check (`socket.isGuest && uid === this.creatorUid`) is
   unchanged; Steam guests can never be the owner because the owner only
   joins over loopback.
3. The per-IP player limit is skipped for Steam sockets (their
   `remoteAddress` is unique per Steam account). Team bans keep working:
   `team.isBanned(remoteAddress, uid)` sees `steam:<id>` and `steam-<id>`.
4. Optional hardening, decide in Milestone 4: verify a Steam auth session
   ticket in the hello (`getAuthSessionTicket` / `beginAuthSession`). Steam
   Networking Sockets already authenticates the remote identity via Steam
   certificates, so this is likely unnecessary.

## Validation

- Jest (`packages/junon-io/test/server/`):
  - `steam_framing.test.js`: text/binary round trip, fragmentation at and
    around the 500 KB boundary, oversize rejection, malformed headers.
  - `steam_socket_bridge.test.js`: a fake parent-port relay opens a Steam
    guest socket against a real standalone server, sends hello + `Ping`,
    receives the reply, joins as `steam-<id>`, gets `PlayerKick` on
    `stopHosting`, and is rejected on a protocol mismatch; a client-supplied
    `steam-` uid over the normal socket is refused.
- `npm exec --workspace packages/junon-io -- jest test/server --runInBand`
  and `NODE_ENV=standalone npm run client:build`.
- Desktop Playwright (`packages/junon-desktop/test/desktop.spec.js`) with
  Steam absent: the app starts, Steam controls are hidden, existing flows pass.
- Manual, two machines, two Steam accounts that are friends, app id 480 or
  the real app id: host on Steam, invite, accept with the game closed and
  open, Join Game from the friends list, play, disconnect, rejoin as the same
  character, rejoin from a second machine with the same account, stop
  hosting (guest sees the reason), host quits (save contains the guest's
  character). Repeat with one side behind a restrictive NAT. Record ping and
  initial-load time versus direct-address co-op.

## Decisions

- 2026-10-14: Binding: `steamworks-ffi-node` (Koffi FFI, Steamworks SDK
  1.64, last release 2026-09-24) over `steamworks.js` (napi-rs; last npm
  release 0.4.0 in 2024-08). `steamworks.js` only exposes the deprecated
  `ISteamNetworking` P2P packet API (1 MB reliable limit, no connection
  state) and lacks rich-presence join and launch-command-line support.
  Greenworks is unmaintained. Writing our own N-API addon was rejected for
  maintenance cost. Revisit if the binding stalls; it sits behind
  `src/steam.js`, so swapping it is local.
- 2026-10-14: Transport: Steam Networking Sockets connection-oriented P2P
  (`connectP2P`/`createListenSocketP2P`), not `ISteamNetworkingMessages`, so
  we get ordered reliable delivery and connection state that map onto
  WebSocket semantics. Not a loopback WebSocket proxy on either side: on the
  host a socket adapter avoids every Steam guest appearing as `127.0.0.1`
  (which breaks per-IP limits and bans and would bypass `isGuest`); on the
  guest the preload transport avoids opening a local listener.
- 2026-10-14: Steam stays in Electron main; the game server stays
  Steam-free and testable with a fake relay. Initializing Steam in the
  utility process as well was rejected (one SteamAPI per app process; the
  overlay needs main).
- 2026-10-14: Direct-address co-op stays. It is the only option for
  non-Steam builds, `npm run server` and the browser client.
- 2026-10-14: No real Steam app id yet. Develop against 480 (Spacewar)
  through `JUNON_STEAM_APP_ID`; the real id becomes the default when
  assigned.
- 2026-10-14: Steam guests are keyed `steam-<SteamID64>`, derived by the
  host from the connection (Milestone 4), not the self-asserted local
  profile id.
- 2026-10-14: Steam lobbies default to Friends only; Invite only is the
  host's alternative.

## Discoveries and risks

- 2026-10-14: `steamworks-ffi-node` 0.11.3 loads in plain Node and fails
  `init` cleanly (returns false) without the redistributable, so the
  no-Steam path is exercised on every run. It depends on `koffi`, whose
  install script npm's allow-scripts doesn't run; koffi's prebuilt
  `@koromix/koffi-*` packages loaded anyway. Packaging must keep `koffi`,
  its platform package and `steamworks-ffi-node` outside the asar.
- 2026-10-14: The team menu's world Preview builds its URL from the game
  connection URL, so a Steam guest (`steam:<id>`) gets a broken image.
  Still open after Milestone 3: serve them over the game socket, or inline
  as `listWorlds` does.
- 2026-10-14: Steam's member list can lag a guest's connection request, which
  is why the host waits for membership instead of checking once. The fake
  Steam delays membership the same way, so the tests exercise the wait.
- 2026-10-14: The server's join traffic is small (about 4 KB up to
  `JoinGame`); the client asks for the rest afterwards. Measure the whole
  initial load over the relay in Milestone 5.

- No automated test can reach real Steam; CI covers framing and the server
  bridge with fakes. Steam-specific behaviour is manual-only.
- Relay latency adds to ping; the game sends state at a fixed rate over a
  reliable channel, as it does over TCP today, so behaviour should match a
  WebSocket on a slower link. Measure in Milestone 5.
- Main-process relay cost: every guest frame crosses main → utility process.
  Fine for a handful of guests; profile with 4+ guests.
- The Electron overlay integration in the binding renders the window into a
  native surface; it may affect input or performance. It is optional.
- `restartAppIfNecessary` must be off in development or `npm run desktop`
  relaunches through Steam.
- Rollback: Steam is feature-detected; removing the dependency or setting
  `JUNON_STEAM=0` returns the app to direct-address co-op only.
